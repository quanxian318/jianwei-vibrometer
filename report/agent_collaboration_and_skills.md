# 智能体协作过程和技能包

## 1. 协作目标与职责划分

本项目围绕“见微视觉测振仪”的需求分析、软硬件划分、程序实现与板级联调，引入OpenAI Codex编码智能体辅助开发。参赛队员负责提出应用需求和工程约束，完成器件连接、供电检查、万用表及示波器测量，并观察屏幕、报警灯、打印纸和扬声器的实际输出；智能体负责读取工程与技术资料、分析运行日志、提出可验证的假设、辅助修改代码、执行构建测试，以及整理版本和验证证据。功能取舍和结果确认由参赛队员结合实物状态完成。

项目采用单一编码智能体与参赛队员协作的形式，智能体依次承担需求分析、编码、测试和工程复核等职责。协作重点是将自然语言需求转化为可检查的工程变更，并利用日志、仪器读数、回归测试和实物反馈约束判断。模型名称及具体版本以原始会话导出信息为准，不以无法核实的模型参数作为开发效果的依据。

## 2. 智能体工作流

团队逐步形成“需求约束—证据采集—问题假设—最小修改—分层验证—结果回写—经验提炼”的工作流。

首先，将需求明确为目标功能、接口条件、允许修改的范围和验收方式。例如，在适配新的Nano固件时保留其既有固件，在修改测频上限时保持摄像头链路不变，在采集停机基线时保持手动照明。其次，由智能体读取原理图、源码、配置、实现报告和运行记录，区分软件配置、接口通信和物理输出三个层面的状态。对尚不能确认的硬件情况，由队员补充测量或观察，避免把指示灯亮、命令返回成功等局部现象直接作为功能完成的依据。

修改前记录原版本、关键配置和文件校验值；修改时优先在独立目录中完成，保留原工程及回退依据。验证按照单元或合成信号测试、主机回归、ARM交叉编译、必要的Vivado实现、设备运行和用户实物确认逐层推进。涉及接线与供电的动作由队员完成，智能体不将远程状态推断为已经执行的物理操作。验证结束后，记录本次变更、验证结果和适用条件，再将重复出现的排查方法提炼为技能包。

## 3. 代表性协作与纠错案例

### 3.1 依据资源报告调整PL/PS分工

开发过程中，团队发现XC7Z010的PL资源趋于紧张，而双目深度并非主测振的必要输出。队员提出将双目深度作为辅助功能，智能体结合工程结构与实现报告，协助移除独立PL深度计算核及其专用互连，保留双路相机采集、三路VDMA、显示、PDM麦克风和灯光链路，并采用PS端低分辨率、低更新率的辅助深度计算方案。

在该架构调整阶段，LUT由13,655降至8,574，BRAM由41.5块降至30.5块，DSP由3个降至0个，Slice由4,400降至4,026。后续加入独立打印UART后，最新实现报告为LUT 8,945、触发器14,420、BRAM 30.5块、Slice 4,017。上述数据分别对应不同功能阶段，不能将功能不同的工程直接作为同条件性能对比。

进一步复核发现，最新工程虽然LUT利用率为50.82%，Slice利用率仍达91.30%，因此资源判断应同时考虑LUT、寄存器、控制集与布局占用。时序报告中WNS为+0.756 ns、WHS为+0.028 ns，但仍有无时钟及未约束端点等检查项；团队据此将表述限定为“已约束路径时序通过”，保留后续完善约束的任务。

### 3.2 根据采样记录修正频率搜索范围

换用约1320转/分钟的电机后，系统多次报告测量无效。智能体最初列出测点位置、背景参考、停机基线和采样频率等可能原因，随后读取实际记录，确认相关采集约45.05帧/秒且没有丢帧，而保存的位移频谱在约21.6 Hz处存在明显峰值。结合队员提供的实测转速，一倍转频约为22 Hz，进一步定位到原算法仅搜索到采样率的0.45倍，即约20.3 Hz，导致相应峰值未进入候选范围。

根据队员“不改变摄像头链路”的约束，程序移除原0.45倍采样率截断，将软件搜索上限设为30 Hz，同时保留奈奎斯特频率以下的频点范围、基线门限和采样质量检查。以生产算法进行合成位移回归，7 Hz、21.6 Hz和22 Hz信号在两个初始相位下通过频率与幅值检查，丢帧及基线采样率不匹配仍被拒绝。该结果验证了软件修改；30 Hz是搜索参数上限，当前约45帧/秒的采样边界仍约22.5 Hz，新电机的完整测量精度与重复性还需板级实验确认。

### 3.3 通过数字预览与实物对照定位打印异常

打印功能恢复后，队员反馈纸条上局部文字被压扁。智能体先检查数字报告的384像素宽渲染结果，确认源图中文字比例正常，再将排查重点转向串口传输与分段打印衔接。程序保留CTS流控，在每24行光栅发送后等待UART排空，并加入120 ms间隔；使用同一份720行报告重打后，队员确认压扁现象恢复正常。

这一案例将“界面生成正确”和“物理打印正确”作为两个独立验收点，通过同源内容对照缩小故障范围。对MMIO诊断脚本中可能引发多次FIFO访问的读写方式，也改用明确的32位访问，并结合寄存器模型与硬件回环结果检查。所得经验可复用于串口打印机、FIFO外设及其他带流控的异步输出设备。

### 3.4 利用反例反馈修正语音与状态判断

在基线结束语音调试中，智能体曾依据播放命令被接受、程序未报错作出较乐观判断；队员指出实际输出整段为杂音后，团队将结论修正为“播放接口可调用，语音内容尚未验证”。随后完成语音资源、基线成功事件与 SD 播放的联合调试，基线完成、测量完成和报警提示均正常播放。

对“音量数字改变但声音不变”的反馈，团队采用已确认正常的同一条语音进行对照，设置0%与40%播放，队员确认第一遍无声、第二遍有声，由此确认音量传递有效，并明确新设置在下一条播放任务生效。界面随后加入音量百分比、生效提示和试听入口。此类反例促使协作过程中持续区分命令成功、数据格式正确、实际内容正确和用户体验符合预期四类证据。

## 4. 技能包的提炼与组织

按照赛题第3.3.5.2节，团队将上述方法整理到独立的`skill/`目录。每项技能均说明来源案例、输入与输出、使用步骤、验证方式及失效条件，以“陌生队伍可理解并迁移”为目标，避免只保存本项目路径和单次操作命令。

| 技能目录 | 可复用内容 | 来源与已验证效果 | 适用边界 |
|---|---|---|---|
| `partition_review` | 软硬件划分提示词及证据检查模板 | 根据PL资源与功能优先级调整辅助深度实现，保留主采集链路 | 需提供目标器件、真实报告和功能优先级，不能按LUT百分比直接推断可布局空间 |
| `sampling_check` | 采样率、目标频率与搜索范围检查脚本 | 由22 Hz信号被原搜索范围排除的问题提炼，包含可测边界与混叠提示 | 只核查必要条件，不证明图像跟踪质量、毫米标定或真实频率准确性 |
| `implementation_audit` | Vivado资源与时序报告核查脚本 | 提取最新工程资源，区分正时序余量与约束覆盖完整性 | 针对英文文本报告，格式或工具版本变化时需检查解析结果 |
| `peripheral_diagnosis` | 串口、打印、语音和触屏的分层排查清单 | 来自字体压扁、音量对照、命令成功但实际为杂音等现象 | 针序、电压和寄存器宽度必须按具体硬件重新确认 |
| `delivery_check` | 文件清单与SHA256核验脚本、提交检查表 | 对当前代码包逐文件校验，保留源码、二进制及历史补丁的对应关系 | 哈希一致只证明文件一致，不替代功能或实物验收 |

其中，脚本采用主机端Python标准库实现；提示词模板由本项目实际工作流提炼，作为可迁移的操作规范，各项技能提供可复跑的主机样例。当前工程使用 Zynq PS/Linux 与 RTL 协同；通用 PYNQ 技能提供契约检查、代码生成和 RTL 仿真示例。

## 5. 协作记录与证据管理

每个案例按“队员需求或提示词—智能体回答及假设—执行动作—验证证据—队员反馈—修正结论—可复用经验”留档。本次附带的交互选摘保留可定位的提示词及模型回应，并标明逐字摘录与过程摘要的区别；正式提交时应同时附上平台导出的原始会话记录及相应日志、测试结果和实现报告。

本项目不以代码生成数量作为智能体贡献的主要依据，而以问题是否得到证据支持、错误判断是否被修正、修改能否复现和验证边界是否明确评价协作效果。整机触屏、Nano 串口、NFC、SD 语音和前面板均已按设计完成联调。团队将每个案例的输入、修改、回归结果和整机表现一起归档，作为复用依据。
